============================================================
问题：miio 协议 device_ts_ 序号不同步导致设备掉线/丢包
============================================================

【背景】
项目通过米家 miio LAN 协议直连 cuco.plug.v3 智能插座（TCP 54321）。
miio 协议要求每个 RPC 请求带递增的 device_ts_（设备时间戳/序号），
设备会拒绝 ts_ 小于等于上次请求的包。

【具体问题】
device_process 启动时本地维护一个 device_ts_ 计数器，每次 RPC 自增。
但设备重启或网络抖动后，设备端的 ts_ 会重置为较小值，而本地计数器
仍是较大值 → 协议序号失步 → 设备拒绝所有请求 → 显示离线。

【排查过程】
1. 现象：插座重启后 device_process 显示设备离线，Hello 握手无响应
2. 抓包分析：用 tcpdump 抓 54321 端口，发现请求包发出但设备不回
3. 协议研究：阅读 miio spec，发现 device_ts_ 必须单调递增，但
   设备重启后实际 ts_ 较小，本地仍发大 ts_ → 设备认为乱序丢包
4. 验证：手动重置本地 ts_ 为 0 后设备立即恢复响应

【解决方案】
1. 握手时从设备 Hello 响应头读取真实 device_ts_
2. 后续 RPC 用这个值作为基准，本地自增
3. 每次 RPC 响应头再次同步 ts_，防止长期漂移

伪代码：
  // Hello 握手
  HelloResp resp = sendHello();
  device_ts_ = resp.server_ts;  // 从响应同步

  // RPC 请求
  RpcReq req;
  req.ts_ = ++device_ts_;       // 本地自增
  RpcResp r = sendRpc(req);
  device_ts_ = r.resp_ts;       // 从响应再同步

【面试要点】
- IoT LAN 协议常有序号/时间戳机制，必须与设备端同步
- 不能假设本地状态在设备重启后仍然有效
- 抓包是排查"发出去没响应"问题的第一步
- 响应头同步是防止序号漂移的通用模式
